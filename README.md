# Sagot AI — Philippine BIR Tax Q&A (Hallucination-Mitigation RAG)

Sagot AI answers questions about Philippine BIR (Bureau of Internal Revenue)
tax regulations — Revenue Regulations, RMCs, RMOs, RAOs, RDAOs, rulings,
bulletins and FAQs — using only a fixed set of official PDFs. The thesis
question is not "can it answer tax questions" but **"can it be stopped from
making things up when it doesn't actually know the answer."**

Every answer is generated by one model and then checked by a **second,
different model from a different company**, against the exact document
excerpts the first model was given. If the check fails three times in a row,
the system refuses rather than guessing. Nothing reaches the user unless it
passed that check.

This document is the manual: what the system is, how a question moves
through it, how to run it, how to share it publicly safely, and how to
manage the corpus, the cache and the logs. It describes the codebase as of
**2026-09-27** (Session 4). If something here doesn't match what's on your
disk, the code is the source of truth — this file can fall behind it.

## 1. How a question is answered (the pipeline)

```
User question
   │
   ▼
1. SANITIZE          clean the text; refuse if too long / too many
   (sanitize.py)      questions / too many issuance numbers cited
   │
   ▼
2. DETECT LANGUAGE    english / filipino / taglish, from word markers
   (language.py)      → decides the language of every fixed message
   │
   ▼
3. GREETING CHECK     a bare "hi" / "kumusta ka" → fixed reply, no model
   (greetings.py)      call, no retrieval
   │
   ▼
3b. INTENT            CHAT ("what can you do?") → fixed reply
   (intent.py)        TAX_COMPUTATION ("magkano tax ko kung 800k…") →
                        deterministic calculator (app/computation/), NO model
                        call; asks for missing inputs over several turns
                      too vague ("tax?", "VAT") → clarifying question
                      everything else → continues below (RAG)
   │
   ▼
4. YEAR ROUTING       an explicit citation ("RMC 34-2024") or a single
   (classifier.py)     unambiguous year → hard-filter search to that year;
                        two different years mentioned → search everything
   │
   ▼
5. ANSWER CACHE       exact-match lookup (SQLite) — a hit returns
   (cache.py)          instantly with no model calls at all
   │  (miss)
   ▼
6. RETRIEVE           semantic search (Jina embeddings + Chroma) AND
   (retrieval.py)      keyword search (BM25), each returns 5, fused by
                        Reciprocal Rank Fusion into the best 5 excerpts
   │
   ▼
7. GENERATE           DeepSeek writes a draft, citing excerpts as [1] [2]…,
   (llm.py)            or replies NO_ANSWER if the excerpts don't cover it
   │
   ▼
8. VERIFY             Qwen (a different vendor) checks every claim in the
   (llm.py)            draft against the SAME excerpts, fails closed on
                        anything unsupported or uncited
   │
   ├─ passed ──────────────────────────────► verified answer, cached, returned
   │
   └─ failed → retry generate+verify, up to 3 attempts total
                 → still failed after 3 → guidance (recovery.py), never cached
```

**Nothing the user sees was written by only one model.** Either a claim
survived a second, differently-sourced model checking it against the actual
source text, or the user gets guidance instead of an answer: an honest "I
don't have enough information in my documents to answer that yet", a
clarifying question, example questions the system can answer, and the
closest documents it found. No model writes that guidance and it states no
tax facts. Tax computations never go through a model at all: the numbers
come from verified rule files in `tax_rules/` and deterministic code. See
`CONVERSATION_AND_COMPUTATION.md`.

### Why two different models

If the same model (or a model from the same lab) both wrote and checked the
answer, it would tend to approve whatever it confidently invented — it
shares its own blind spots. The generator (DeepSeek) and verifier (Qwen) are
from different companies for this reason. `.env` warns you on startup if
they're ever set to the same model.

### What the verifier does and does not catch

The verifier checks that a claim **appears in the retrieved excerpts** — it
does not check that the excerpts themselves are correct. If a scanned PDF
was misread by OCR (a real issue: see `RDO No. 938` vs. the likely correct
`93B` in one RAO document), a faithful answer that repeats the OCR error will
still pass verification, because it *is* faithful to what the excerpt says.
The system defends against the model inventing facts, not against bad source
text. Sources flagged `· OCR` in an answer are exactly the ones to double
check against the original PDF.

## 3. First-time setup (Windows / PowerShell)

```powershell
# From the project root
python -m venv venv
venv\Scripts\Activate.ps1

python -m pip install -r requirements.txt
python -m pip install pymupdf pytesseract pillow rank_bm25   # confirm these landed; see note below
```

> **Note on `requirements.txt`:** it currently carries some packages the app
> no longer uses (`streamlit`, `altair`, `pydeck`, `scikit-learn`, `groq`,
> `langchain-groq`) — harmless but due for cleanup. The line above makes
> sure the packages the app *does* need (PDF OCR, BM25) are actually
> installed, since a stale `requirements.txt` can silently skip them.

**Install Tesseract itself** (the OCR *program*, separate from the
`pytesseract` Python package): download the Windows installer from
<https://github.com/UB-Mannheim/tesseract/wiki>. If it isn't on your PATH
afterward, point to it explicitly in `.env`:

```
TESSERACT_CMD=C:\Program Files\Tesseract-OCR\tesseract.exe
```

**Create `.env`** in the project root (never commit this file):

```
OPENROUTER_API_KEY=sk-or-...
JINA_API_KEY=jina_...

# Public-demo safety (see section 6). Lower this before sharing a link.
DAILY_QUERY_CAP=100
```

See section 8 for every other setting you can add here.

**Put PDFs in `data/`**, one folder per source year (`data/2024/`,
`data/2025/`, …) or `data/faq/`. See section 5 for adding documents later.

**Build the index:**

```powershell
python -m app.database --reset
```

This loads every PDF, OCRs any scanned page that has no real text layer, and
writes the vectors to `chroma/`. Read the console output — it reports how
many pages were loaded per folder and flags any file that still has empty
pages (meaning OCR didn't produce anything for it).

## 4. Running the server

**Locally only** (nobody outside your computer can reach it):

```powershell
venv\Scripts\Activate.ps1
uvicorn main:app --host 127.0.0.1 --port 8000
```

Open <http://localhost:8000> in a browser. `--reload` (auto-restart on code
changes) is fine for development:

```powershell
uvicorn main:app --host 127.0.0.1 --port 8000 --reload
```

**To stop:** `Ctrl+C` in the terminal running uvicorn. **To leave the venv:**
`deactivate`.

### Sharing it publicly through ngrok

The UI, `/query`, `/status` are meant to be reachable by anyone with the
link; `/upload` and `/reset` are meant to stay yours alone. `app/guard.py`
enforces that split — see section 6 before you run this for the first time.

```powershell
# Terminal 1 — the app, bound to localhost only
uvicorn main:app --host 127.0.0.1 --port 8000

# Terminal 2 — the tunnel
ngrok http 8000 --url https://your-subdomain.ngrok-free.dev
```

Use **your own** reserved ngrok subdomain (ngrok's free plan gives you one
fixed URL) rather than a random one, so it doesn't change every restart —
but treat that URL as a real credential: **do not commit it into a public
GitHub repo.** If it's already in `README.md` history, rotate it (get a new
one from the ngrok dashboard) rather than assuming an old commit won't be
found.

## 5. Managing the document corpus

### Option A — drop files in and re-ingest (recommended for bulk additions)

1. Copy new PDFs into the right year folder under `data/`, e.g.
   `data/2026/RMC No. 12-2026.pdf`. Any folder under `data/` works, not only
   the known year names — see `app/database.py`'s docstring — but only years
   listed in `classifier.KNOWN_YEARS` (`2001–2003, 2022–2026`) can ever be
   hit by the year-citation filter in section 1, step 4.
2. Re-run ingestion:

   ```powershell
   python -m app.database
   ```

   This only adds chunks for files it hasn't seen before (matched by
   filename + page), so it's safe to run after adding a handful of new
   files — existing chunks are left alone. Existing files are only
   re-processed if their content changes AND you use `--reset` (full
   rebuild), because chunk ids are stable across runs otherwise.

3. **Full rebuild** (needed after changing OCR settings, or if you suspect
   the index is stale/inconsistent):

   ```powershell
   python -m app.database --reset
   ```

   This deletes `chroma/` entirely and reloads everything from `data/`. It
   also clears the answer cache automatically (old answers may no longer
   match a changed index).

### Option B — upload through the running app (`/upload`)

The chat UI itself doesn't expose an upload button, but the endpoint exists
and can be called (from **this computer only** — see section 6) with:

```powershell
curl.exe -X POST http://localhost:8000/upload `
  -F "file=@C:\path\to\RMC No. 12-2026.pdf" `
  -F "category=2026"
```

`category` should be one of the existing year folder names to stay
searchable by the year filter; leave it out and the file goes into
`data/` directly, tagged `"uncategorized"` — still searchable by BM25 and
semantic search, just never hard-filtered by year.

### Checking what actually got indexed

```powershell
python check_scans.py                 # which PDFs have scanned pages, and what OCR will do
python check_ingestion_coverage.py    # PDFs on disk vs. what Chroma actually has, plus zero-text files
```

Run `check_scans.py` first — it's fast (no OCR, just checks for images) and
tells you which files need Tesseract at all. Run
`check_ingestion_coverage.py` after `--reset` to confirm nothing silently
failed to load.

## 6. Running this safely as a public demo

`app/guard.py` handles all of this automatically once the server is running
— nothing extra to launch — but you should understand what it's protecting
against before you share a link:

| Protection | What it stops |
|---|---|
| **Daily question cap** (`DAILY_QUERY_CAP`, default 100) | A shared link draining your $10 OpenRouter balance. Worst case is ~1.1¢/question (3 full attempts, every token cap hit), so 100/day ≈ $1.10/day max. |
| **Per-visitor rate limit** (`RATE_LIMIT_PER_MIN`, default 6) | One visitor spamming questions. Uses the *last* address in the tunnel's forwarding header, so a visitor can't dodge it by sending a fake one. |
| **`/upload` and `/reset` locked to this computer** | Anyone with the public link wiping your corpus or adding files. Blocked for any request arriving through the tunnel, from another machine, from another website's page (even one open in *your* browser), or via a domain rigged to resolve to `127.0.0.1`. |
| **No CORS** | The UI is served by this same app, so it never needs cross-origin permission — removing it closes off a whole class of "a website tricks your browser into calling your own API" attacks. |
| **DOMPurify on every answer** | A model output that happens to contain HTML/script tags is sanitized before being shown — matters more once answers can be cached and re-served to other visitors. |

**Before your first public demo:**

1. Set `DAILY_QUERY_CAP=100` (or lower) in `.env`.
2. On openrouter.ai, consider setting a spending limit on the API key itself
   — a second line of defense if something here has a bug.
3. Confirm `/reset` returns `403 Forbidden` from outside — open
   `https://your-ngrok-url/reset` (as a plain GET, which FastAPI will
   reject as method-not-allowed *after* the guard check) or test with curl
   from another machine.
4. Don't commit your live ngrok URL to a **public** GitHub repo — copy the
   command in section 4 into a local note instead of into `README.md` if
   your repo is public.

## 7. The answer cache

Exact-match only (not semantic): "RMC 24-2026" and "RMC 25-2026" must never
share an answer, so the cache key is the literal normalized question, plus a
fingerprint of the index contents and every setting that affects the
answer. Only **verified** answers are ever cached — refusals and errors
never are.

```powershell
python -m app.cache --stats     # entry count, total hits
python -m app.cache --clear     # delete every cached answer
```

**Clear the cache after:**
- editing `app/classifier.py` (the year-filter regex isn't in the
  fingerprint — the year filter it applies isn't fingerprinted, only the
  models/prompts/retrieval settings are)
- editing `app/retrieval.py`'s `source_label()` formatting
- any change that isn't a model name, prompt, or retrieval-tuning constant
  (those ARE auto-detected and invalidate the cache on their own)

You do **not** need to clear it after re-ingesting documents —
`add_to_chroma()` and `clear_database()` in `app/database.py` already clear
it for you automatically.

`bypass_cache: true` in a `/query` request skips both reading and writing
the cache — use this for every evaluation run, so you're always measuring
the live pipeline.

## 8. Logs and traces

### Per-question trace (`logs/queries.jsonl`)

Every `/query` call — whether it succeeds, refuses, or errors — appends one
JSON line here: the cleaned question, language, year filter applied, every
retrieved excerpt (with its text, since a re-index can change a chunk's
text under the same id), every generator draft, every verifier verdict and
critique, which host served each model call, cost, latency, and the final
outcome.

```powershell
python -m app.trace              # summary: outcome counts, attempts, total cost
python -m app.trace --last 5     # the 5 most recent traces, in full
```

This file is **not committed to git** (`.gitignore` covers `logs/`) and
**should not be shared as-is** — it contains visitors' raw questions and
unverified draft answers. It's the raw material for your thesis evaluation:
judging *rejected* drafts against the excerpts is how "hallucinations
caught" gets measured, and only this file keeps rejected drafts at all — the
UI never shows them.

### Console output

While `uvicorn` is running, each question prints a sequence of tagged lines
you can follow live:

```
🔍 [Router] Query: '...'              — the incoming question
📅 [Year Filter]: ... / none          — whether a year filter was applied
💾 [Cache] hit / miss / bypassed      — cache outcome
🔀 [RRF] inputs: ...                  — how many docs each retriever contributed
🧼 [Sanitize] rejected (...)          — only printed if the question was refused
💸 [LLM:generator] model via Host ... — every model call: tokens, host, cost, time
✅ [Verifier] attempt n/N: supported  — verification passed
❌ [Verifier] attempt n/N: rejected — <critique>
🙅 [Generator] ...: NO_ANSWER
```

### Model usage totals (this process, since it started)

From a Python shell with the venv active:

```powershell
python -c "from app import llm_client; print(llm_client.usage_summary())"
```

Cross-check this and the trace log's summed cost against OpenRouter's own
Activity page (openrouter.ai/activity) periodically — the trace log's `cost`
field is whatever OpenRouter's API reported per call, which is usually but
not always populated.

## 10. Design decisions worth knowing before you change something

- **Versions.** The running version is in `app/version.py` (shown on the demo page and recorded in every evaluation `summary.json`); `VERSIONS.md` lists what each version changed and the `.env` settings that reproduce an older one.
- **Dense-search floor (v1.3).** The reranker keeps only 1–3 excerpts and could drop a chunk dense search ranked highly. The top 4 dense hits are now added back after the cut (up to 6 excerpts), so Sagot AI's evidence always includes what a standard dense-only RAG sees, plus the BM25, issuance-match and reranker results. The verifier checks the answer against all of it. `DENSE_FLOOR_K=0` turns it off.
- **Concise generation prompt (version 2; version 3 is the default).** The original prompt
  asked for a restated first sentence plus two or three supporting bullets
  (median 88 words in the query logs). Version 2 follows the standard RAG
  prompt's direct style (1–3 sentences, about 60 words) and keeps everything
  the pipeline relies on: grounding-only, `NO_ANSWER`, the language
  instruction, `[n]` citations and the verifier's audit notice. Retrieval,
  the verifier and fail-closed refusal are unchanged. `RAG_PROMPT_VERSION=1`
  restores the original prompt (to reproduce `rag_eval/results_v2`).
- **No query rewriter, no translation step.** The system answers directly in
  whatever language the question was asked in; nothing is generated in
  English and translated afterward (which would add an unverified step
  after verification).
- **History is off by default.** Every question is answered standalone. This
  was a deliberate fix (see git history) for two bugs: history made almost
  every cache lookup miss, and letting the generator see earlier answers let
  it reuse facts the verifier never checked.
- **The year filter only fires when exactly one year is in play.** Two
  citations, a citation plus a different bare year, or a range like
  "2024-2025" all back off to searching the whole corpus, so an amendment in
  a different year isn't silently excluded.
- **Verification is fail-closed.** Anything other than a clean
  `{"verdict": "SUPPORTED", "issues": []}` — malformed JSON, "SUPPORTED" with
  issues still listed, a verdict the parser doesn't recognize — is treated as
  a failure. The system would rather refuse than guess.
- **The answer cache is exact-match, not semantic**, specifically so it
  can't confuse two different issuance numbers or a typo'd percentage.

## 12. The evaluation tool (thesis evaluation)

A second page, served by the same server, that scores chatbot answers with the thesis metrics. Open it from the **Evaluation** button in the chatbot's header (it opens in the same tab; **Back to chatbot** returns you, but an ongoing chat is cleared), or go straight to <http://localhost:8000/eval>.

**One-time setup** (on top of section 3):

```powershell
pip install -r rag_eval/requirements.txt
```

and in `.env`, a judge model that is **not** the generator or the verifier (the system must not grade itself):

```
JUDGE_MODEL=openai/gpt-4o-mini
```

If the extras aren't installed, the chatbot still starts and only `/eval` is missing (a warning is printed).

**The four data points.** Every evaluation uses a *question*, the *context* (document excerpts the chatbot read), the chatbot's *answer*, and a *ground truth* (the correct answer, written from the official document). For Sagot AI, context and answer are produced automatically (it is asked live, cache skipped). For another chatbot such as REVIE, you paste its answer; REVIE shows no context, so its Groundedness and Context Relevance are shown as "—" with the reason, never as 0. An optional *expected language* (english / taglish) feeds the language-trigger scores.

**Scores.** Groundedness, Context Relevance and Answer Relevance (the SOP's three RAGAS metrics); Answer Correctness (supplementary: the only score that uses the ground truth, and the fair Sagot AI vs. REVIE comparison); Trigger Precision, Trigger Recall and False Positive Rate (Sagot AI's language detector, over a package). The **How it works** tab explains each one in plain language.

| Tab | What it does |
|---|---|
| How it works | The four data points and every score, explained for a non-technical reader |
| Test one question | Sagot AI, another chatbot, or both side by side. "Fill with a thesis example" loads any T-TED question |
| Test a package | Upload a CSV/JSON (download the template from the page) or load the T-TED dataset; runs in the background with progress and a Cancel button; averages, trigger scores, paired statistics, per-question drill-down, CSV download. Runs are saved in `rag_eval/results/web_runs/` and can be reopened |
| Thesis results | RQ1 / RQ2 / RQ3, computed live from the offline run's checkpoint (below) |

**Cost and the public link.** Every test makes paid model calls (chatbot + judge + Jina), so the run buttons only work on the host computer (`localhost`). Visitors on the ngrok link can read the guide and the thesis results but cannot start tests (`EVAL_LOCAL_ONLY=1`, the default). Only one package test runs at a time, and a one-call preflight checks the judge before any chatbot call.

**The offline thesis run** (what the Thesis results tab reads):

```powershell
python -m rag_eval.run_evaluation --subset A --limit 4   # smoke test
python -m rag_eval.run_evaluation --subset all           # full run; re-run the same command to resume
python -m rag_eval.run_evaluation --rq2-only             # RQ2 only, free
```

Results: `rag_eval/results/summary.json`, `scores_flat.csv`, `raw_scores.json`. Every answer is checkpointed in `rag_eval/results/checkpoint.jsonl` as soon as it is scored; a crash never means paying again. When the way answers are scored changes (a new metric), re-running re-scores the saved answers without calling the chatbot again.

## 13. The live demo page (for the panel)

A third page, served by the same server, for showing the system live: <http://localhost:8000/demo>, or the **Live demo** button in the chatbot's header. It is kept calm for the panel: it opens as a plain chat with **Sagot AI only**, and each answer shows only its text (long answers such as a tax computation fold, with **Show full answer**). Everything else stays hidden until clicked: the guide (**Guide**), the comparison and reference-answer settings (**Options** next to the question box), and under each answer three buttons, **Sources**, **Scores** and **How it was made**. With a comparison, **Compare the scores side by side** opens one small bar chart per score. While a system works, one plain-language line says what it is doing. Behind those buttons:

1. **The process, live.** An architecture strip (Input check → Language trigger → Intent & routing → Hybrid retrieval → RRF fusion → Reranker → Generator ⇄ Verifier → Answer) lights up as each stage runs, and a step-by-step log underneath shows what happened: the chunks each search found, what the reranker kept, every draft, every verifier verdict and retry, and the final outcome. Stages a turn doesn't use (a computation, a greeting) are shown struck through.
2. **Three scores** from the independent judge model (`JUDGE_MODEL`), each with its formula one click away:

| Shown as | How it is computed on this page |
|---|---|
| Groundedness | claims supported by the retrieved documents ÷ all claims in the answer (same as the evaluation) |
| Context Relevance | average cosine similarity between the user's question and 3 questions generated from the answer (the evaluation's Answer Relevance formula) |
| Answer Relevance | facts in the operator's reference answer stated correctly ÷ all facts in the reference answer (the evaluation's Answer Correctness formula); N/A when no reference answer is typed |

**Compare with REVIE** (under **Options**) runs the same question through Sagot AI and shows REVIE's answer next to it. Ask REVIE the same question on the BIR website and paste its answer into the **REVIE's answer** box first. **Compare the scores side by side** then shows both systems' three scores.

Since v1.5 the demo compares Sagot AI with REVIE only. The LLM-only (C0) and standard-RAG (C1) baselines were offered up to v1.3/v1.4 and removed: after the dense-search floor, standard RAG showed no meaningful difference, so the demo focuses on the project versus the existing BIR chatbot. Their code is in git tag `v1.3` (`app/baselines.py`) if the ablation is needed again.

"N/A" means a score does not apply (REVIE shows no retrieved documents, so it has no Groundedness), never zero.

Files: `static/demo.html`, `static/js/demo.js`, `static/css/demo.css`, `static/js/team-access.js`, `rag_eval/demo_web.py` (page + streaming run endpoint `/eval/api/run/demo`), `rag_eval/demo_metrics.py` (the three scores), `app/progress.py` (the live step events; a no-op for the normal chatbot and the evaluation). Tests: `tests/test_demo.py`.

**Evaluation button hidden for the defense.** The **Evaluation** button is hidden on the chatbot and the demo so the panel isn't drawn to it; `/eval` itself works as before. To bring the button back, open <http://localhost:8000/?eval=1> once (remembered in that browser); `?eval=0` hides it again.

**Cost and access.** The demo runs on the host computer, or for teammates on the public link who enter the team access code (see section 14). The cache is always bypassed so every step runs live. A question costs roughly Sagot AI's 2–6 model calls plus 3 judge calls and 1 Jina embedding call per system shown.

## 14. Sharing with teammates (public link)

`SHARING.md` has the full guide. In short:

1. Put `TEAM_ACCESS_CODE=<8+ characters>` in `.env`.
2. Double-click `share.bat`. It starts the server and a free Cloudflare tunnel, and prints a public `https://….trycloudflare.com` link.
3. Send that link and the code to your teammates.

Over the public link, the chatbot works for anyone, within the per-person and daily limits. The demo and the evaluation tool ask for the team code once. `/upload` and `/reset` stay host-only. A `Dockerfile` is included for always-on hosting (for example Hugging Face Spaces); see SHARING.md, Option B.

| Variable | Default | Meaning |
|---|---|---|
| `TEAM_ACCESS_CODE` | *(unset)* | Code that lets teammates on the public link run the demo and evaluation tool. Unset = host computer only |
